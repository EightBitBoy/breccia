# Performance baseline, 2026-11-25 (plan 18)

The numbers before plan 18's fixes: the core's measures (`crates/core/tests/it/scale.rs`) and the window's
(`app/e2e/perf-scale.mjs`). Plan 18's Task 7 measures again and compares against this file.

## Machine and commit

- CPU: Intel Core i7-13700H (20 logical processors); RAM 32 GB; display about 127 Hz (one frame is 7.9 ms).
- Windows 11 Pro 10.0.26200; Git 2.45.2.windows.1; Node 24.19.0; Rust 1.90; release builds.
- Commit `c0018fa` plus the Task 2 measuring scripts (no app or core code changed).
- The installed Breccia was not used: every launch has its own `BRECCIA_CONFIG_DIR` and WebView2 profile, off screen.

## Commands

- Core: `cargo test --release -p breccia-core -- --ignored --nocapture scale::` (tests `scale_5000_pages`,
  `scale_5000_extras`, `git_at_scale`; each line is a median of 5 to 21 samples in one process).
- Window: `just perf-scale` (release exe; one discarded warm-up launch for Windows Defender's first-read scan, then 3
  measured launches, each on a fresh config dir so the search index is cold; each line is the median of the 3).

## The two folders

- Core (`scale.rs`, its own generator, in-process): 5,000 notes files, which the app lists as **5,005 pages**: the five
  tags `#t0`, `#t4`, `#t8`, `#t12`, `#t16` are linked-only pages on top of the 5,000. The Git measures use a repository
  of 3,000 commits, pushed to a local bare remote, and a second clone whose remote was never pushed to.
- Window (`scaleFolder.mjs`, the folder of `just graph-scale`): 2,000 pages in 50 folders and 3,000 journal days with
  50,000 links, plus a page `Hub` linked from 1,000 pages and days, 3,000 archived tasks (one per journal day), a page
  `Long page` of 5,000 rows, and a Git repository of 3,000 commits: 5,002 notes files, 54,000 links. No remote (the
  remote's cost is measured in the core), `[git] commit_delay_minutes = 0` and `pull_interval_minutes = 0`, so every
  launch starts from the same files; today's journal day is empty at each start.

## How the window numbers are taken

- `window shows`: spawn to the WebView's first contentful paint (`performance.timeOrigin` plus the paint entry).
- `journal usable`: spawn to the first row of the journal (today's empty day: its "start writing" row). It comes
  before `window shows` because the app inserts the row before the window's first paint: today the folder opens
  inside the shell's setup, so the window paints nothing until the open is done.
- `typing during first build`: 40 keys typed into today's journal day while the status bar shows the index item
  (20 letters, each followed by Enter; about 150 ms in all). The editor saves 300 ms after the last key, so letters
  alone would be one save; each Enter saves at once. The p95 is over the 22 saves of each launch (`block.setText` and
  `block.split` trace lines under `BRECCIA_TRACE=1`). The first build ends about 2.8 s after the spawn, 1.5 s after
  the journal shows, too soon for 40 keys with pauses between them.
- `search during first build`: Ctrl+K, then the query `links`: the input event to the first full-text hit. The index
  was still building at the input in every launch. No bar (owner Q2 b, pre-flight F8).
- Git history: the click on the status bar button to the first row; each "Show more" to its new rows (the line is
  the slowest of the 10); then wheel steps to the end of the 2,200 rows. Archive: the click to the first row, then
  wheel steps to the end of the 3,000 rows. Frames are the gaps of a `requestAnimationFrame` loop.
- `caret down`: 50 ArrowDown presses from the first row of `Long page`, each key to the next animation frame.
- `journal scroll back 500 days`: wheel steps from today until day 500 is rendered (about 350 steps).

# Page colors Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A page can be given one of 25 fixed colors, and every top-level block of a journal day whose first topic
link or tag goes to a colored page is shown, with its sub-blocks, on a soft wash of that color.

**Architecture:** The core reads and writes a `color::` line in a page's preamble (new module `color.rs`), resolves
each top-level journal block's first topic link through the existing link resolution, and puts the result into the
journal's `BlockView`s. A page's color change, creation, deletion or alias change marks its keys, and `Session::run`
re-sends the journal days that link to them. The frontend draws the washes from `BlockView.topic`/`color` (pure
run logic in `app/src/lib/pageColors.ts`), and a swatch plus a 5 × 5 picker on the page title row sends
`page.setColor`. Every shade is a token in `tokens.css`.

**Tech Stack:** Rust (breccia-core), Tauri 2 (no shell change), Svelte 5 + TypeScript, bits-ui Popover, Vitest,
Playwright e2e over WebView2.

**Spec:** `docs/superpowers/specs/2026-11-07-page-colors-design.md` (binding), plus `docs/spec.md`, `docs/format.md`
and `CLAUDE.md`.

## Global Constraints

- Only the one `color::` line changes in a notes file (spec §2 anti-goal); files Breccia did not change stay
  byte-identical. A save still writes LF, as every save does today (format §3).
- The value written is a color name from the fixed set, in lower case, never a hex value.
- `color::` is a page-level preamble line; front matter is never changed and a `color` key in YAML front matter is
  not read. The key is matched ignoring ASCII case, like `title::`. In journals `color::` is not read.
- The `color::` line that gives the color is hidden in the page view, the way the `title::` line is.
- A pick is its own undo step (owner, 2026-11-07): undo brings the old color back or removes the line, redo puts it
  back, and earlier undo steps of the page stay.
- Only journal days (feed and a day opened as a page) show washes. Not the page tree, links, linked references,
  search, graph, boards or All pages.
- Only top-level blocks decide; sub-blocks always take their parent's color. Links to journal days and to pages that
  do not exist are skipped; the first topic page decides even when it has no color.
- Tags count exactly like links; a link through an alias takes the aliased page's color.
- Consecutive top-level blocks resolving to the same page form one blob; blocks resolving to different pages are
  separate blobs with a visible gap, even when the colors are equal.
- Wash target: the page color's theme shade at 28 % on Light and Taupe, 34 % on Dark, Violet and Graphite, 30 % on
  Teal (Teal tuned down so its dim text stays readable; see Task 5).
- No colour literals or `color-mix` outside `app/src/styles/tokens.css` (`theme.test.ts` checks it). The System
  theme's dark block must equal the Dark block (checked).
- Tauri event names stay `noun:verb`; new struct fields go at the end of their struct (serde `preserve_order`, the
  frontend's echo check compares `JSON.stringify`).
- Commits: conventional subjects; `feat`/`fix` subjects are user-facing changelog lines (no code names, paths, task
  numbers), at most about 90 characters, no trailing period. Internal work is `test`, `refactor`, `docs`, `chore`.
  No attribution lines. Commit on `main` and push after each commit.
- Every test must fail first: capture the RED run before implementing.
- `App.svelte` has no unit tests: logic with tests goes in `app/src/lib/`.
- e2e steps assert the bytes on disk where a file changes, and wait for states instead of sleeping.

## Review Focus

- A page file with CRLF line endings, or whose last line has no line break (a file with no blocks), gets a color:
  only the `color::` line is added (plus the LF a save always writes); pinned in Task 1 (`recolor` without
  terminator, CRLF) and Task 2 (`set_color_on_a_crlf_file_adds_only_the_line`).
- Another program (a Git pull) changes a page file after Breccia read it, then the user picks a color: the pick is
  refused with the usual changed-on-disk error and the file is untouched; pinned in Task 2
  (`set_color_refuses_unknown_names_journals_and_changed_files`).
- A colored page's `color::` line is changed or removed from outside (Git pull, another editor) while the journal
  feed is shown: the washes follow without a reload; pinned in Task 3
  (`an_outside_color_edit_updates_the_journal_days`).
- Undo and redo around a pick: Ctrl Z after a pick, after typing then a pick, after a Git pull rewrote the file, and
  redo after undo; the user expects the old color back, the typing still undoable, nothing undone over an outside
  edit, and the journal washes to follow each step; pinned in Task 2 (`a_pick_is_its_own_undo_step`,
  `an_outside_edit_ends_undo_of_a_pick`), Task 3 (`undoing_a_pick_updates_the_journal_days`) and Task 8 (step 112).
- Folding a colored block, or selecting rows inside a blob: the blob is drawn over the visible rows only and keeps its
  rounded ends; selection stays visible over a wash; pinned in Task 4 (`washRows` on rows with a folded subtree left
  out) and Task 6 (CSS order: `.block.selected` after the wash rules).

### Shades per theme

- Produces (in `breccia_core::color`):
  - `pub const PAGE_COLORS: [&str; 25]` in the grid order above.
  - `pub fn canonical_color(name: &str) -> Option<&'static str>`: the entry of `PAGE_COLORS` equal to `name`
    ignoring ASCII case, else `None`.
  - `pub fn color_line(preamble: &str) -> Option<(usize, &'static str)>`: the first property line after the front
    matter whose key is `color` (ASCII case-insensitive, via `inline::property`) and whose value is a page color:
    its index among `preamble.split('\n')` and the canonical name. Same conventions as `inline::title_line`.
  - `pub fn page_color(preamble: &str) -> Option<&'static str>`: `color_line(..).map(|(_, c)| c)`.
  - `pub fn recolor(preamble: &str, color: Option<&str>, le: LineEnding) -> String`:
    - `Some(c)`: the first `color::` property line after the front matter (any value) becomes `color:: c`, in place,
      keeping its line ending. Without one, `color:: c` + `le` is inserted directly after the first valid `title::`
      line, else as the first line after the front matter. A line it is inserted after that has no terminator gets
      `le` first (as `pages.rs::retitle` does after front matter).
    - `None`: every `color::` property line after the front matter is removed (any value).
    - Front matter is never changed. The caller passes only canonical names.

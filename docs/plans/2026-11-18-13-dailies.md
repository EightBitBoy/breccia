# Plan 13: Dailies Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A new view, Dailies: a flat list of things to tick each day. A checked daily sinks to the bottom, greyed and
struck through; the status bar counts the open ones; every daily starts afresh at a reset time set in Settings
(default midnight). The list lives in `breccia/dailies.md`.

**Architecture:** The core reads and writes `breccia/dailies.md` with the existing outline parser (one top-level block
per daily, a `checked:: YYYY-MM-DD HH:MM` property for the last check) and answers new `dailies.*` commands. It never
decides whether a daily counts as checked: the window computes that from the `checked::` time and
`[dailies] reset` in `breccia/config.toml`, and a timer redraws at the next reset. Nothing is written at reset time.

**Tech Stack:** Rust 1.90 (`crates/core`, `app/src-tauri`), Svelte 5 + TypeScript, Vitest (node, no DOM),
pragmatic-drag-and-drop, Playwright e2e over WebView2 (`app/e2e/smoke.mjs`).

**Spec:** this plan's "Owner decisions" (binding), `docs/spec.md` (§2 anti-goals, §4, §5, §6, §7.1, §7.12, §7.13; a
new §7.14 written in Task 10), `docs/format.md` (§2, §8, §11, §14).

## Summary for the owner (plain words)

What you get: a "Dailies" entry in the sidebar, under Journal. It opens a list of things you do every day, each with a
checkbox. Ticking one moves it to the bottom, greyed and struck through; unticking brings it back. You add a daily in
the field at the bottom, click its text to change it, right-click to delete it (Breccia asks first), and drag
it (or `Alt ↑` / `Alt ↓`) to change the order. When every daily is ticked, the view says "All done for today". The
status bar shows "Dailies 3 open", or "Dailies ✓" when all are done; a click opens the view. Every day at the reset
time (Settings > Dailies, midnight unless you change it) all ticks are gone again, even if Breccia was closed or the
PC was asleep. The list is the file `breccia/dailies.md`, readable in any editor and synced by Git like your notes.

The tasks:

1. The core reads and changes the list in `breccia/dailies.md`, keeping everything else in the file byte for byte.
2. The reset time `[dailies] reset` in `breccia/config.toml`, with the same handling of a wrong value as the Git
   minutes have.
3. The core's commands: list, add, check, uncheck, edit, delete, move.
4. Changes from another program or a Git pull show at once; the Git commit message says "dailies".
5. The rules for "checked today" and the next reset, with tests for midnight, a 04:00 reset, summer time, a sleeping
   PC and a clock set back.
6. The window's Dailies state: the list, the timer, the status bar item.
7. The Dailies view, its sidebar entry, Back and Forward, the status bar item.
8. Settings > Dailies: the reset time.
9. End-to-end steps that check the bytes on disk.
10. The spec, the format description (version 9), the word list and the review items.

## Owner decisions (2026-11-18)

Recorded verbatim from the owner's answers.

1. Storage: a Markdown file `breccia/dailies.md` in the notes folder. One top-level block per daily; its text is the
   daily's text; a `checked:: YYYY-MM-DD HH:MM` property (plain value, NOT a [[link]], local time) holds the last check
   time. Example:

   ```markdown
   - Check emails
     checked:: 2026-11-18 07:42
   - Do the time logging
   ```

2. Reset is computed, never written: a daily is checked iff its `checked::` time is at or after the most recent reset
   moment. Nothing rewrites the file at reset time. Unchecking removes the `checked::` line. The file order is the
   user's order; sorting checked dailies to the bottom is display only (spec anti-goal §2: never reorder/reformat user
   text; round trip must keep unchanged blocks byte-identical; unknown properties/text kept).
3. Naming: the view is "Dailies", one entry is "a daily" ("Add a daily"). Add to docs/vocabulary.md.
4. Status bar: left item "Dailies N open"; when all are checked it shows "Dailies ✓"; click opens the view. (Decide and
   state what shows when there are no dailies at all — propose hiding it, as a ruling the owner can see.)
5. Reset time is shared, in breccia/config.toml: `[dailies] reset = "00:00"` (HH:MM, PC local time), set in a new
   Settings > Dailies section; config.toml must keep comments and unknown keys; follow the plan-11 handling for
   invalid/out-of-range values. Example: reset 04:00 → a check at 01:30 counts for the previous period.
6. Out of scope, to go into docs/backlog.md as new numbered items when the plan finishes (list them in the plan):
   weekday-only dailies (e.g. `days:: mon-fri`), a history/streaks log, groups of dailies (e.g. Morning/Evening).
7. One flat list.

Design suggestions the owner has seen and that this plan follows: sidebar entry near Journal and Boards, part of Back
and Forward; checkbox and text rows, click to edit inline, context menu Delete, drag to reorder (writes the file
order), "Add a daily" field at the bottom, an "All done for today" note, checked rows greyed and struck through and
sliding to the bottom (no animation with reduced motion); `dailies.*` commands, a `dailies:changed` event, the
watcher follows outside edits and Git pulls, `breccia/` is not indexed; the period logic in `app/src/lib/dailies.ts`
with Vitest tests; one timer to the next reset plus a re-check on focus, visibility and wake.

## Rulings made while writing the plan

Each is binding unless the owner overrides it at review. "Cost if wrong" is what changes later.

- **W1. No dailies, no item.** With no dailies at all (no file, or a file without blocks), the status bar shows no
  Dailies item. Cost if wrong: one line in `dailiesItem`.
- **W2. Text is plain.** A daily's text is its block's first line, shown as plain text: no Markdown, `[[x]]` and
  `#tag` are not links. `breccia/dailies.md` is not indexed: no search hits, no linked references, no graph, no tags
  (owner: dailies are not linked to pages). Cost if wrong: render through the core's inline HTML and decide on links.
- **W3. What else may be in the file.** A preamble, nested blocks under a daily, continuation lines, unknown
  properties, a BOM and CRLF are kept as text. Nested blocks are not shown; they move and are deleted with their
  daily. Only top-level blocks are dailies. An edit replaces only the first line; check and uncheck touch only the
  `checked::` line. Saved files get LF, as every notes file (spec §4). Cost if wrong: show nested lines dimmed.
- **W4. `checked::` values.** Read: `YYYY-MM-DD HH:MM`, also `YYYY-MM-DD HH:MM:SS` (seconds dropped) and a plain
  `YYYY-MM-DD` (counts as 00:00). Anything else (a `[[link]]`, a word) counts as not checked and is kept as it is; a
  check replaces it. Only the first `checked::` property line is read; uncheck removes every one. `checked::` keeps its
  plain meaning in pages and journals. Cost if wrong: a parser tweak.
- **W5. A check from the future counts.** A `checked::` time later than now (the clock was set back, another PC's
  clock) is at or after the last reset, so the daily shows as checked. Cost if wrong: one comparison.
- **W6. Delete asks first; no undo** (owner answer to Q1, 2026-11-18). "Delete" in a daily's menu opens a confirm
  ("Delete the daily 'Check emails'?", buttons Delete and Cancel, Esc cancels), using the app's existing confirm
  dialog where it fits. The Dailies view has no undo or redo of its own. Cost if wrong: adding undo later means two
  commands and a session stack.
- **W7. Never write over an outside change.** Before each change the core reads the file again. If it changed since
  Breccia read it, the new text is taken first (dailies whose block did not change keep their id) and the change is
  made on it; if the daily is gone, the change is refused with "This daily changed in another program; the list now
  shows the file as it is." A failed write keeps the list as it was and says so (there is no "unsaved" daily). Cost if
  wrong: per-page style conflict notices.
- **W8. Reset value rules.** `reset` must be a string `HH:MM`, 00:00 to 23:59, two digits each. A string that is not
  (`"24:00"`, `"4:00"`, `"4am"`) is read as `"00:00"` with one notice naming it; the file is not changed (plan 11).
  A value of another type (`reset = 4`) refuses the file, like any wrong type. The Settings field also takes `4:00`
  and writes `"04:00"`. `[dailies]` with `"00:00"` is not written into a file that lacks it; the default config of a
  new folder does not list `[dailies]`. Cost if wrong: one more accepted form.
- **W9. Sidebar place.** "Dailies" sits right under "Journal" (above "All pages"), with a ☑ glyph like the other
  entries. Back and Forward step through it like the Archive. Cost if wrong: move one block in `Sidebar.svelte`.
- **W10. Reordering.** A row is dragged within its own group (open among open, checked among checked); the file
  order changes so the daily sits right before the daily it was dropped above (or after the group's last one).
  `Alt ↑` / `Alt ↓` on a focused row do the same by one place. Cost if wrong: allow drops across groups (they would
  only reorder the file, since the group follows the check).
- **W11. Timer.** One timer to the next reset, plus a re-check on window focus, on `visibilitychange`, and once a
  minute (the minute tick catches a PC that slept across the reset and a clock that was changed, where a timer can
  fire late or never). Cost if wrong: none for the user; a tick a minute is cheap.
- **W12. Format version 9.** `docs/format.md` §1: the version goes up when a file that already exists would be read
  differently. A `breccia/dailies.md` was ignored ("Nothing else in `breccia/` is read") and is now read, so the
  version goes to 9. Cost if wrong: one history line.
- **W13. Git commit messages** name a change to `breccia/dailies.md` as `dailies` (next to `settings`). Two PCs that
  tick the same daily between syncs can conflict in Git like any file; Breccia's conflict handling (spec §7.9) applies.
- **W14. Settings field.** A plain text field (like the Git minutes), not a time picker, which would follow the
  system's 12-hour format. Hint: "This computer's time. A daily ticked before it counts for the day before."

- **W15. Where the format description puts it.** `docs/format.md` gets a new last section, "## 15. Dailies", after
  the format history, and §1's "The history at the end" becomes "The history in section 14". Sections 11 to 14 are
  cited by number in the spec, the code and older plans, so nothing is renumbered. Cost if wrong: a renumbering.

## Global Constraints

- Spec anti-goal §2: never silently drop, reorder or reformat text the user wrote. A daily the user did not change
  keeps its bytes; a file Breccia did not change keeps its bytes; `breccia/config.toml` keeps comments and unknown keys.
- `checked::` value format, written: `YYYY-MM-DD HH:MM` local time, from the command's `Clock` (`now.format("%Y-%m-%d
  %H:%M")`). Reset format: `HH:MM`, default `"00:00"`.
- Command names keep dots (`dailies.list`); the event is `dailies:changed` on the wire; payloads keep struct field
  order (serde_json `preserve_order`). Every new command gets its `CommandKind` (`dailies.list` is a Query, the rest
  are Edits) and its TypeScript type in `app/src/lib/types.ts` (the contract test checks names).
- Every test must be able to fail: capture the RED run before the change. A pin of behaviour that already holds is
  shown to fail by a temporary mutation, noted in the task report.
- Logic that needs tests goes into `app/src/lib/` (Vitest in node, no DOM); `App.svelte` and components have no unit
  tests.
- No colour literals or `color-mix` outside `app/src/styles/tokens.css`. Greyed rows use the existing muted-text
  token; the strike-through is `text-decoration: line-through` as on finished cards.
- Motion: the slide of a checked row is about 150 ms, none with `prefers-reduced-motion: reduce`.
- e2e: assert the bytes on disk where a file changes; wait for states, never sleep; baseline 208 PASS lines, last
  step 137; new steps from 138. Run `just e2e` after Tasks 7, 8 and 9. The counted number goes into `docs/STATUS.md`.
- Commits: conventional subjects, one change per commit. `feat`/`fix` subjects are changelog lines in plain user
  words (no code names, paths, task numbers; at most about 90 characters; no trailing period). Core and plumbing work
  that no user sees on its own is `chore`, `test` or `docs`. No attribution lines. Commit on `main`; no push until the end of the plan (Q4).
- `docs/review.md` items start at 115, under `## Dailies (plan 13)`. New backlog numbers start at 92.
- Vocabulary: "Dailies" (the view), "a daily" (one entry), "Add a daily", "check"/"uncheck" in code and docs, "tick"
  is fine in user texts. Never "habit", "routine" or "todo" for a daily.
